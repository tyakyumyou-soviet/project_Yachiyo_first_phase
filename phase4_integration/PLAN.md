# Phase 4: System Integration (システム統合とWebアプリ化) 完全計画・技術仕様書

## 0. 2026-05-07 改訂方針（優先）

本節は既存の詳細設計より優先する。詳細な変更仕様は ../PLAN_CHANGE_SPEC_2026-05-07.md を参照する。

- **Phase 4の役割**: Phase 1〜3で作った実証パーツを1つのWindowsアプリ/システムとして統合する。
- **Phase 2との境界**: Phase 2の時点でPhase 1とUIの最小統合は済ませる。Phase 4では、TTS、リップシンク、supervisor、runtime mode、LAN/Tailscale運用まで含めた完全統合と安定化を担当する。
- **優先順位**: `localhostで統合成功` → `LAN/Tailscale IPでアクセス` → `必要ならHTTPS/PWA`。セキュリティより、まず動くことを優先する。
- **HTTPS**: Tailscale Serve + MagicDNS + HTTPS は推奨だが必須ではない。mkcertも開発用/代替として残す。ぶっちゃけ動けばよい。
- **GPUメモリ**: RTX3060の専用VRAM 12GBを性能予算にする。共有GPUメモリ8GBに頼る設計は禁止。共有メモリ使用を検出したら軽量モードへ落とす。
- **プロセス管理**: `start_yachiyo.bat` だけでなく、Windows用 `yachiyo_supervisor.py` で Ollama / Backend / TTS / Frontend の起動、ログ分離、health checkを行う。
- **runtime mode**: Normal / Voice Stable / Text Rich / R&D TTS / Reasoning を用意し、LLM/TTS/STTの同居負荷を切り替える。
- **LLM運用方針**: 統合の現行本命は `Qwen3-VL 8B` とする。ただし、リアルタイム性やagent応答速度で優位が確認できた場合は `Gemma 4 26B A4B + MTP` へ比較移行できるよう、supervisor、設定、health checkはモデル差し替え可能な構造を保つ。

## Part 1: プロダクトビジョンと統合要件（何を作るのか）

### 1. プロジェクト目標
フェーズ1（LLM/脳）、フェーズ2（アバター/UI）、フェーズ3（TTS/声帯）の3つの独立したシステムを統合し、1つの「AI秘書Webアプリケーション」として完成させる。
ホストPC（Windows / RTX 3060）上で全てのコアプロセスをローカル稼働させつつ、外出先のスマホやMacのブラウザからVPN経由で安全にアクセスし、ヤチヨと対話できる環境を構築する。

注意点として、Phase 2の時点で既に Phase 1 <-> Phase 2 の最小統合は完了している前提とする。Phase 4はそこから先の「全体を1つの製品として無理なく動かす」工程であり、初回の接続確認フェーズではない。

### 2. 統合における3つの最大の課題と解決目標
本プロジェクトのハードウェア環境（RTX 3060 VRAM 12GB）において、各プロセスのVRAM配分を適切に管理し、以下の目標を達成するアーキテクチャを設計する。

1. **VRAMの管理**: 12GBのVRAM内で、Ollama（LLM）とStyle-Bert-VITS2（TTS）が互いにメモリを食い潰してクラッシュしないよう、安全な境界線を引く。2GBの安全マージンを確保する。
2. **超低遅延パイプライン（ストリーミング）**: ユーザーの発話完了から、ヤチヨが喋り始めるまでのタイムラグを**「1〜2秒以内」**に抑え、自然な会話のテンポを実現する。
3. **セキュアなリモートアクセス**: 危険なポート開放（ポートフォワーディング）を行わず、安全に外部デバイスからホストPCのシステムにアクセスする。

## Part 2: 技術仕様と統合アーキテクチャ詳細（どう繋ぐのか）

### 3. プロセス・オーケストレーション（全体構成）
ホストPC上では、以下の4つのプロセスが同時に稼働する。

| プロセス | 役割 | 使用技術 | ポート |
|:---|:---|:---|:---|
| **Process A** | LLM推論エンジン | `Ollama` | `:11434` |
| **Process B** | 音声合成API (Phase 3) | `FastAPI` (Style-Bert-VITS2) | `:5000` |
| **Process C** | 統合バックエンド (Phase 1) | `FastAPI` (Python) | `:8000` |
| **Process D** | Webフロントエンド (Phase 2) | `Vite` (React) | `:5173` |

- **起動スクリプト**: これら4つのプロセスを1クリックで同時に起動・終了できる `start_yachiyo.bat` を作成し、運用を自動化する。

### 4. VRAM 12GB 配分戦略
メモリ不足によるCUDA Out of Memoryエラーを防ぐため、以下の制約をシステムレベルで強制する。

#### 4.1 LLMのVRAM配分
- **モデル選定**: パラメータ数 8B 以下のモデルを 4-bit 量子化（Q4_K_M 等）で使用する。
- **コンテキスト長**: Ollama起動時に `num_ctx` を **16384** に設定。VRAM 12GBの余裕を活かし、記憶をより長く保持できる。VRAM使用量は**最大6GB**。

#### 4.2 TTSのVRAM配分
- Style-Bert-VITS2は推論時に **約2.5GB** を消費する。
- FastAPI起動時にPyTorchのVRAMアロケータを制限する（`PYTORCH_CUDA_ALLOC_CONF` の設定）。
- これにより「LLM(6GB) + TTS(2.5GB) + OS(1.5GB) = 10GB」となり、**2GBの安全マージンを確保**したまま12GBの枠内に収まる。

### 5. 超低遅延パイプライン：チャンク分割ストリーミング
「LLMが全テキストを生成し終わるまで音声合成が始まらない」という遅延を防ぐため、**句読点ベースの非同期パイプライン**を実装する。

#### 5.1 処理フロー（Process C: 統合バックエンド内）
1. LLMからストリーミングでテキストを受信開始。
2. テキストバッファに文字を溜め、**「。」「！」「？」「\n」**が来た瞬間に、そこまでのテキストを1つの「チャンク（塊）」として切り出す。
3. 切り出したテキストチャンクを**即座にProcess B (TTS) へ送信**し、音声合成を開始する。
4. その間も、LLMは次の文章の生成（ストリーミング）を継続している。
5. 音声が出来上がったら、WebSocket経由で Process D (UI) へバイナリ送信する。

#### 5.2 UI側の再生キューイング（Process D: Webフロントエンド内）
- UI側は音声チャンクを受信した順に `AudioQueue`（配列）に格納する。
- 前のチャンクの音声再生が終わった瞬間に、シームレスに次のチャンクを再生する。
- これにより、**「LLMが最初の1文を考え終わった瞬間」にヤチヨが喋り始め**、裏で次の文章と音声が作られ続けるため、人間と同じテンポで対話できる。

### 6. セキュアなリモートアクセスとネットワーク設計
外出先のスマホや別室のMacからヤチヨにアクセスするためのインフラ設計。

#### 6.1 Tailscale (VPN) の導入
- 自宅のルーターに穴を開ける（ポート開放）のはセキュリティリスクが極めて高いため**絶対に行わない**。
- 代わりに完全無料のVPNサービスである **Tailscale** をホストPCとスマホ/Macにインストールする。
- Tailscaleが割り当てる固定のプライベートIP（例: `100.x.x.x`）経由でのみアクセス可能とする。

#### 6.2 CORS（オリジン間リソース共有）設定
- Process C (Phase 1) および Process B (Phase 3) のFastAPI設定にて、CORSを許可する。
- 許可するオリジン（Origins）は、`http://localhost:5173` と `http://100.x.x.x:5173` (Tailscale IP) のみに限定し、不正なアクセスを弾く。

#### 6.3 HTTPSとマイクの権限問題
- ブラウザの仕様上、`Web Speech API` (マイク) や `AudioContext` を使うには、原則として **HTTPS環境** または **localhost** である必要がある。
- Tailscale環境下ではlocalhostではないため、マイクがブロックされる可能性がある。
- **対策**: Viteの `vite-plugin-mkcert` 等を使用して自己署名SSL証明書を発行し、ローカルネットワーク内でHTTPS化（`https://100.x.x.x:5173`）してマイク権限をクリアする。

### 7. フォールバック（縮退運転）モード
外出先で通信環境が悪い場合や、ホストPCで重いゲームをしていてVRAMが使えない場合のためのセーフティネット。

- **テキストチャット専用モード**: UI上のトグルボタンで「音声合成OFF」「リップシンクOFF」にするモード。TTSによるVRAM消費と、音声データの通信量（帯域幅）をゼロにし、純粋なテキストチャット＋表情・モーションのみで軽量に動作させる。

### 8. UIデザインシステム（統合時の共通仕様）
UIの視覚的な統一仕様はフェーズ2のPLAN.md §5〜§8 に詳細が定義されている。統合時に遵守すべきポイント:

- **カラーパレット**: 「月見＝月夜」テーマ。ベース `#0a0e1a`（夜空の紺）、アクセント `#d4af37`（月光の金）、セカンダリ `#9b8ec4`（薄紫）、テキスト `#e8e4df`（月白）。
- **レイアウト**: アバター全面型。チャットは右下にグラスモーフィズムでオーバーレイ。ダッシュボードはトグル式。
- **背景カスタマイズ**: デフォルトは夜空×月光の画像。ユーザーが任意の画像をアップロードして差し替え可能。「デフォルトに戻す」ボタンでいつでも復帰。画像は `localStorage` に保存。
- **レスポンシブ**: PC（1024px〜）はアバター全面＋右下チャット、タブレット（768〜1023px）は縦分割、スマホ（〜767px）はアバター上1/3＋チャット下2/3。

### 9. PWA（Progressive Web App）対応
スマホのホーム画面から直接起動できるネイティブアプリライクな体験を提供するため、PWA化を行う。

- **`manifest.json`**:
  - `name`: 「月見ヤチヨ」
  - `short_name`: 「ヤチヨ」
  - `theme_color`: `#0a0e1a`
  - `background_color`: `#0a0e1a`
  - `display`: `standalone`（ブラウザUIを非表示にしネイティブ風に表示）
  - `icons`: 月のモチーフアイコン（192x192, 512x512）
- **Service Worker**: `vite-plugin-pwa` で自動生成。アプリシェル（HTML/CSS/JS/VRMモデル）をキャッシュし、2回目以降の起動を高速化する。
- **オフライン時の挙動**: UIシェルのみキャッシュで表示可能。LLM・TTSはホストPC依存のため、通信切断時は「ホストPCに接続できません。再接続を試みています...」の画面を表示し、指数バックオフで自動再接続を試行する。
- **HTTPS要件**: PWAの登録にもHTTPSが必須。§6.3の自己署名SSL証明書でこの要件を同時にクリアする。
